# LoRa Protocol Specification (Binary)

This document describes the binary transmission format, frame layout, and reliable ACK/retry exchange used between **Sensor Nodes** (ESP32-C3) and the **Gateway** (ESP32-C6).

The protocol is optimized to minimize radio frame size (within the constraints of LoRa's limited bandwidth) while ensuring data authentication, message sequence tracking, dynamic timeouts, and retransmissions.

---

## 1. Over-The-Air Frame Structure

Each packet transmitted over LoRa uses an AES-128-GCM encrypted layout wrapped by a 9-byte plaintext transport header:

| Offset (bytes) | Field | Size (bytes) | Description | Visibility |
|---|---|---|---|---|
| `0` | Frame Header | `9` | Node ID, 32-bit sequence number, message type (`MSG_TYPE_DATA` / `MSG_TYPE_ACK`), and 3 bytes entropy. Used as Authenticated Associated Data (AAD) & IV. | Plaintext |
| `9` | Payload | `N` | Encrypted payload (`SensorPayload` for DATA or `AckPayload` for ACK). | Encrypted |
| `9 + N` | Auth Tag | `8` | Message Authentication Code (MAC) generated by AES-128-GCM (`TAG_SIZE = 8`). | Plaintext |

---

## 2. Frame Header Layout (`HDR_SIZE = 9`)

The 9-byte header (`HDR_SIZE = 9`) identifies the sender/receiver, tracks sequence numbers, specifies message type, and provides initialization vector (IV) entropy material for AES-128-GCM:

| Byte Offset | Field Name | Type / Format | Description |
|---|---|---|---|
| `0` | `node_id` | `uint8_t` | Unique node identifier (0–254) |
| `1 .. 4` | `seq` | `uint32_t` (Big-Endian) | 32-bit monotonically increasing sequence number |
| `5` | `msg_type` | `uint8_t` | Message type (`0x01` = `MSG_TYPE_DATA`, `0x02` = `MSG_TYPE_ACK`) |
| `6 .. 8` | `entropy` | `uint8_t[3]` | 3 random bytes from hardware TRNG to ensure unique AES-GCM IVs |

### Message Types (`MessageType`):
- **`MSG_TYPE_DATA` (`0x01`):** Transmitted by Node $\rightarrow$ Gateway containing encrypted `SensorPayload`. Requires Gateway ACK.
- **`MSG_TYPE_ACK` (`0x02`):** Transmitted by Gateway $\rightarrow$ Node containing encrypted `AckPayload`.

## 3. Reliable Transport (ACK / Retries / Deduplication)

### Exchange Sequence (Normal Case)
```
NODE                                         GATEWAY
  │                                             │
  │─── 1. DATA (seq=123, msg_type=0x01) ───────>│ (Decrypts & validates AES-GCM)
  │                                             │── Saves/publishes sensor readings
  │                                             │── Builds & sends ACK (seq=123, msg_type=0x02)
  │<── 2. ACK (seq=123, msg_type=0x02) ─────────│
  │                                             │
  │─── 3. Enters Deep Sleep immediately!        │
```

### Exchange Sequence (Lost ACK & Gateway Deduplication)
```
NODE                                         GATEWAY
  │                                             │
  │─── 1. DATA (seq=123) ──────────────────────>│ (Receives & processes DATA seq=123)
  │<── ❌ ACK Lost                             │ (Sends ACK)
  │                                             │
  │    (ACK Timeout reached)                    │
  │─── 2. DATA Retry #1 (seq=123) ─────────────>│ (Detects seq <= last_seq -> DUPLICATE)
  │                                             │── Ignores payload (no double publish)
  │<── 3. Resends ACK (seq=123) ────────────────│── Resends ACK immediately
  │                                             │
  │─── 4. Enters Deep Sleep immediately!        │
```

### Dynamic ACK Timeout Calculation:
The node calculates its ACK reception timeout dynamically using RadioLib's Time-on-Air calculation:
$$\text{ack\_timeout\_ms} = \frac{\text{radio.getTimeOnAir}(\text{ACK\_FRAME\_SIZE})}{1000} + 250\text{ms}$$
*(Where 250ms covers Gateway processing, AES-GCM crypto execution, radio mode switching, and hardware SPI execution).*

## 4. Gateway Decision Tree & Session Handling

The Gateway tracks each node's active boot session via `session_id` (`entropy` material) and handles sequence numbers through a deterministic decision tree:

```
                 session_id (random_id)
                           │
          ┌────────────────┴────────────────┐
          │                                 │
     Différent                          Identique
          │                                 │
    REBOOT/RESET                       Vérifier seq
  (Increment reboots                        │
   & process payload)              ┌────────────┼────────────┐
                                   │            │            │
                               == n.seq       +1          > n.seq+1
                                   │            │            │
                               DUPLICATE      NORMAL       PERTE
                           (Resend ACK      (Process     (Increment
                            & return)        payload)     lost count)
```

1. **New Session / Reboot (`session_id` changed)**:
   - Increments `n.reboots++`.
   - Resets tracked sequence `n.seq = seq` and updates `n.last_random_id = session_id`.
   - Processes the first payload of the new session and responds with ACK.
2. **Duplicate / Retransmission (`session_id` identical AND `seq == n.seq`)**:
   - Increments `n.duplicate_packets++`.
   - Resends ACK via `sendAck()`.
   - Returns early without double-publishing sensor readings.
3. **Packet Loss (`session_id` identical AND `seq > n.seq + 1`)**:
   - Calculates lost frames `n.packets_lost += (seq - n.seq - 1)`.
   - Processes payload normally.

## 5. Diagnostic Metrics & RadioLib Error Mapping

| RadioLib Code | Constant | Meaning / Cause | Gateway Dashboard Handling |
|---|---|---|---|
| `-7` | `RADIOLIB_ERR_CRC_MISMATCH` | Frame CRC check failed (RF noise / collision) | Logged in RF Diagnostic breakdown; does not trigger App Error Badge |
| `-6` | `RADIOLIB_ERR_RX_TIMEOUT` | Receive operation timed out | Logged in RF Diagnostic breakdown |
| `-3` | `RADIOLIB_ERR_LORA_HEADER_DAMAGED` | Physical LoRa header corrupted | Logged in RF Diagnostic breakdown |

*Note: Application Error Badge counts data integrity failures: Lost Packets, Malformed Payloads, and Unknown Node IDs.*

### A. Data Payload (`SensorPayload`)
```cpp
struct SensorPayload {
  uint8_t count;               // Number of readings present (max 10)
  uint8_t reset_reason;        // Last ESP32 reset reason
  uint8_t error_code;          // System error code (0 = OK)
  uint16_t tx_interval;        // Transmission interval (seconds)
  char name[8];                // Node name (8 chars, null-terminated)
  SensorReading readings[10];  // Active readings array (13B header + N × 5B)
} __attribute__((packed));
```

### B. Acknowledgment Payload (`AckPayload`)
```cpp
struct AckPayload {
  uint8_t  node_id; // Destination Node ID
  uint32_t seq;     // Confirmed 32-bit sequence number
  uint8_t  status;  // Status code (0 = OK)
} __attribute__((packed));
```
